## O motor

```js
// main.js:585-592 — dispara em TODO carregamento de página
document.addEventListener('DOMContentLoaded', () => {
    const savedLang = localStorage.getItem('preferredLang') || 'pt';
    applyTranslations(savedLang);
});

// main.js:124-132
const dict = store[lang] || store['pt'];
document.querySelectorAll('[data-i18n]').forEach(element => {
    const key = element.getAttribute('data-i18n');
    if (dict[key]) { element.innerHTML = dict[key]; }
});
```

Três consequências:

1. **Roda sempre**, mesmo em PT, mesmo sem o usuário tocar no seletor.
2. **`innerHTML`**, não `textContent` — o valor pode conter `<br>`, `<em>`, `<strong>`.
   Também significa que o valor da chave é injetado como HTML: não colocar conteúdo
   vindo de fora ali.
3. **`if (dict[key])`** — chave ausente, `undefined` ou string vazia deixa o HTML
   intacto. É a brecha que permite texto fixo (removendo o atributo) e também o que
   mascara chaves faltando: parece funcionar em PT e falha em EN.

`changeLanguage(lang)` grava em `localStorage.preferredLang` e reaplica. Exposto como
`window.setLanguage`.

|---|---|---|---|

| `fr` | 233 | 20% | ❌ |
| `de` | 233 | 20% | ❌ |
| `no` | 233 | 20% | ❌ |

O seletor só oferece **PT e EN** (`data-lang="pt"` e `data-lang="en"`). Os outros
cinco só são alcançáveis via `localStorage.preferredLang` ou `setLanguage('es')`.
Como `dict = store[lang] || store['pt']` **não faz merge**, nesses idiomas as ~80%
de chaves faltantes caem na brecha do `if` e exibem o **texto do HTML, em português**.

**Ao criar chaves novas, preencher `pt` e `en`.** Os outros cinco são um projeto
inacabado; não é obrigatório mantê-los sincronizados.

## Estrutura de `languages.js`

```js
const translations = {
    pt: { chave: "valor", ... },   // linha 2
    en: { ... },                   // ~linha 1191
    es: { ... }, it: {...}, fr: {...}, de: {...}, no: {...}
};
window.translations = translations;
```

Ao inserir chaves por script, **inserir logo após a linha `pt: {` / `en: {`** (topo do
bloco). Inserir "no fim do bloco" é frágil: já houve inserção que caiu depois da chave
`}` de fechamento e quebrou a sintaxe do arquivo inteiro. Depois de qualquer edição
programática:

```bash
node --check assets/js/languages.js
```

## Regra de ouro: toda chave nova entra em `pt` E `en`, no mesmo arquivo

Isso vale nos **dois** arquivos que definem chaves ativas — `languages.js` e
`languages-pages.js` — cada um com seus próprios blocos `pt`/`en` (ver tabela acima).
Adicionar só em `pt` é o erro mais comum e o mais silencioso: o site em português
parece perfeito, o site em inglês mostra a chave crua ou cai na brecha do `if` e
exibe português. Depois de editar, rode:

```bash
python .claude/skills/site-4watt/scripts/auditar.py
```

O item `[2] CHAVES SEM TRADUCAO EM EN` do auditor pega exatamente esse erro.

**Nunca adicione chaves em `languages-core.js`.** Esse arquivo não é carregado por
nenhuma página (confirmado por grep em todos os HTMLs) — é código morto. Qualquer
chave criada ali não tem efeito nenhum, e o sintoma ("editei mas não aparece") é
idêntico ao de uma chave sem `data-i18n`, o que atrasa o diagnóstico.

## Armadilha: `languages-extended.js`

```js
const EXTENDED_LANGS = ['es', 'it', 'fr', 'de', 'no'];   // main.js:4
```

Se o idioma pedido estiver em `EXTENDED_LANGS` **e não existir** em
`window.translations`, `main.js` injeta dinamicamente
`assets/js/languages-extended.js?v=1.2` — **arquivo que não existe no repositório**.

Hoje não quebra, porque os cinco idiomas estão em `languages.js` e o `return`
antecipado impede o carregamento. **Se alguém remover esses blocos para enxugar o
arquivo, o site passa a tentar carregar um 404.** Remover os blocos exige remover
também `EXTENDED_LANGS` e o `loadExtendedTranslations` em `main.js`.
